## 3. scripts 解依赖正确性

### ❌ 硬阻断：仓库根仍是机器固定路径，可能跨 checkout 混读

多个脚本仍用以下固定路径作为 `REPO`：

- `scripts/gate-checks.py:31`
- `scripts/rebuild-exceptions.py:39`
- `scripts/complete-exceptions.py:34`
- `scripts/analyze-gate3.py:9`
- `scripts/list-hits.py:10`
- `scripts/redact-tokens.py:25`
- `scripts/mirror-sync.py:235`

核心问题出现在 `gate-checks.py`：

- `:37` 的 `STANDARDS_SCAN_DIR` 可以指向当前评审 checkout；
- 但 `:43-45` 的 exceptions、overrides、evidence 仍固定指向 `~/Documents/trae_projects/agent-collaboration-standard`。

因此可能发生：

> 用评审分支 checkout 的 `governance/` 做扫描，却拿另一份 canonical checkout，甚至 master 的 `archive/` exceptions 做集合比对。

这会造成门禁 3/4 **跨提交混读**，出现错误放行或错误阻断。独立 clone 后也不能只靠 `STANDARDS_SCAN_DIR` 完整切换评审对象。

**具体修法：**

1. 默认仓库根改为脚本自身推导：
   `Path(__file__).resolve().parents[1]`。
2. 如需覆盖，增加统一的 `REPO_ROOT` 环境变量。
3. `STANDARDS`、exceptions、overrides、evidence、redaction 扫描目录必须全部从同一个 `REPO_ROOT` 派生。
4. 启动时校验这些路径属于同一仓库根，并输出当前 commit SHA。
5. 增加测试：在两个不同 checkout 中运行门禁，确保不会读取另一 checkout 的 archive。

### ❌ 硬阻断：`mirror-sync.py --apply` 仍可反向覆盖 git 真值

`scripts/mirror-sync.py:229-233` 仅添加风险注释，但实际逻辑仍是：

- `:234-235`：旧快照为源、git 仓库为目标；
- `:244-261`：多个映射继续执行 mirror；
- mirror 带删除语义；
- `:278-279` 仍公开提供 `--apply`。

具体失败场景：

> 用户或自动化按旧操作运行 `mirror-sync.py --apply`，脚本将冻结且滞后的旧快照重新覆盖 `governance/`，并可能删除仅存在于 git 真值中的新文件。

注释不能形成执行保护，因此“只加注释不动逻辑”在 Phase D 后仍是实质性破坏入口。

**具体修法：**

- 本轮最安全的最小修复是：检测到 `--apply` 时直接退出非零，明确说明 Phase D 后旧方向已禁用。
- 保留 dry-run 仅用于审计也应醒目标记为 legacy。
- 如要反转同步方向，应另立规格和独立评审，不能直接机械交换源、目标。

## 4. fail-closed 语义闭环

### ❌ 硬阻断：门禁算法本身改善，但输入真值未形成同一提交闭环

积极部分：

- 扫描基准切到 `governance/` 是正确方向。
- `STANDARDS` 不存在时会阻断。
- 门禁 3 不直接信任 exceptions，门禁 4 独立进行集合登记核验，整体设计比早期 tautology 更可信。
- Python 改动均通过语法编译检查。
- 757 行材料 patch 与实际 Git diff 完全相同。

但由于第 3 项所述的**混合仓库根**问题，门禁可能把一个 checkout 的治理文档与另一个 checkout 的 exceptions/overrides 比较。因此当前还不能认定门禁 3/4 对“被评审的同一 commit”形成可信闭环。

**具体修法：**

- 先统一 `REPO_ROOT`。
- 门禁启动时打印并落证据：
  - repo root
  - 当前 branch
  - `HEAD` SHA
  - governance/archive/patterns 实际路径
- 拒绝 governance 与 archive 不属于同一仓库根的运行。
- 在 detached HEAD 或临时 clone 上重新跑完整四门禁。

### ⚠️ 软观察：patterns 双份保留存在漂移风险

旧位置冻结、新位置成为唯一读取源，作为迁移期安排可以接受；但目前“冻结”主要依赖文档声明。

建议：

1. 新位置设为唯一可写源。
2. 门禁检测旧、新位置同时存在时，只比较摘要，不打印敏感内容。
3. 若摘要不一致，给出明确警告或阻断。
4. 后续经用户授权再安全清理旧副本。
