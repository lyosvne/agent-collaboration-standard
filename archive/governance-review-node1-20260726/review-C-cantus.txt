## 一、5 个本质问题回答

**1. 真值一致性**
终局真值位置应该是 2 个且已由蓝图定死：git（代码+规则的硬真值）+ Aetheris（运行时真值/记忆），本方案与此对齐。但方案只完成"一次性追平"，写入路径未改变——X/Y/Z 三选项中只有 X（软链）和 Y（改引用）真正消灭双存储，Z 本质上是把两套存储制度化，直接违背 §三.3，不应作为平级选项呈给用户。

**2. 冗余消除**
计划阶段允许"先盘点后消除"，D1 的审计路径是对的。但 D1 已预写结论（"推测应该是 unified"），而文档去留属不可委托清单——计划里可以给分析和建议，不该在方案文本里预设权威文档，节点 3 的"用户逐份确认"设计正确，前提是执行时不带引导性预设。

**3. 语义错误修正**
同步方案（文档 2）明确只同步不改内容，语义修正留给 D1——这个分层是正确的架构决策：先保住数据（durability）再修正确性（correctness），顺序不能反。但需注意：同步进 git 的 unified 仍含 CC 引用，节点 2 评审时不应把"内容仍有语义错误"判为同步失败。

**4. 时序版本机制**
§5.3 的 `/truth/versions` 是正确方向但架构归属错了。编队已有真值校验机制——Pi 漂移治理 cron（30min 只读体检→分级报告），文档版本校验应纳入 Pi 漂移治理的扫描范围（把 agent-collaboration-standard 仓库加入体检对象），而不是在 dispatch-server 上另建一套平行机制。两套校验机制本身就是新的"两份权威"。且该机制目前只是"后续基础设施"，无 owner 无排期——在机制落地前，单一真值仍靠人工纪律，这正是这次散乱的根因。

**5. 不可委托敬畏**
整体设计正确：分批授权、红线动作列明、节点 3 用户逐份确认。两处越界需修正：① Step 4 的 commit message 预写了"~/.agent-collaboration/ 作为符号链接或废弃"——X/Y/Z 用户尚未裁决，commit 不应预载结论；② D1 的"推测 unified 为权威"同前述。

## 二、架构级风险（5 个）

**R1（高）Step 2 脚本与红线声明自相矛盾——密钥会被复制进仓库工作区。**
§2.2 说"rsync 排除 cc-retirement"，但 Step 2 实际脚本是 `for d in archive ...; cp -r ~/.agent-collaboration/$d/* $d/`，无任何排除——含明文 token 的 `archive/cc-retirement-20260726/` 会被原样复制进 git 工作树，防线只剩 Step 3 的 .gitignore（且依赖目录名精确匹配）。这是纵深防御坍缩成单点防御。另外更本质的问题：**这些是"今天刚删的明文 token"，无论是否进 git，只要曾落盘就应轮换**——方案只防"进 git"，不要求轮换，不满足 O1 退出条件"不担心密钥会泄"。

**R2（高）一次性同步治标，写入路径不变则漂移必然复发。**
散乱的根因是 agent 的写入路径（~/.agent-collaboration/）与真值路径（git 仓库）分离。方案把长期机制寄托在"今后所有改动直接在 git 做"的纪律声明上——历史已证明该目录"从未全量同步过"，纪律不可靠。不改写入路径（X 或 Y）+ 不上自动校验，三个月后会需要 O1.5 治理。

**R3（中）真值校验机制与 Pi 漂移治理平行建设，违背单一机制原则。**
见问题 4。编队协作机制中"检测不一致→分级报告→授权内代劳"的管道已存在于 Pi，另建 `/truth/versions` 独立端点会形成两套校验真值的机制，本身就是方案要治理的那类冗余。

**R4（中）直接 push master 与编队红线"agent 只在 agent/<name> 分支、master 变更必经审批"存在口径冲突。**
文档 2 §4.1 声明"本仓库个人维护，不走 PR"。若 agent-collaboration-standard 豁免于分支纪律，应由用户显式裁定并写入规则；否则应走 sync 分支 + 用户批准合并。不能靠单份方案自行豁免——这恰是规则文档需要"唯一权威"的原因。

**R5（低-中）三方评审的独立性与吞吐问题。**
评审方 A/B 都是 Mira（同一工具两个模型档），"三方"实际是两方，独立性弱于表述；且编队状态显示 Mira 仍是 pending。4 个节点全部要求三方一致通过，对一个卫生治理工程是过重的串行门——建议只对节点 1（计划）和节点 3（文档去留，触及不可委托）保持三方一致，节点 2/4 降为单评审方 + 用户抽检。
