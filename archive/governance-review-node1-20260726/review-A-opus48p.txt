# 评审方 A（Cloud-O-4.8 Max）— O1 治理计划评审意见

先给结论定位:这套材料的**安全脚手架**（备份 tag/branch、归档优先、红线授权、不可委托敬畏）是真实到位的,不是走过场;但**"建立单一真值"这一核心命题在方案里尚未真正成立**——同步动作会把已知缺陷带进 git,而"单一存储"的决策被推迟。以下按第一性原理逐条拆。

---

## 一、5 个本质问题的回答

**1. 真值一致性——是否真建立"单一真值",还是把两套合成更大的两套?**
没有真正建立。文档2的同步只是让 git **一次性追平** local,但写入入口问题未解:§5.2 的选项 X/Y/Z 被推迟裁决,而选项 Z 明确保留两套存储、直接违背北极星 §三.3。在 X 或 Y 落地前,系统仍是"两个可写存储 + 人工同步"。**终局应只有 1 个真值位置(git 仓库)**,local 要么是软链(X)、要么被消除(Y);Z 应被否决而非并列为等价选项。

**2. 冗余消除——是否真消除,还是暂时搁置?**
搁置了。unified 与 workspace-collaboration-v2.1 在同步清单里都标为 SAME/已同步,即同步步骤会把**两份重叠标准原样推进 git**,而"选唯一权威"的 D1 排在更晚的节点3。批次顺序(先同步、后 D1)导致"单一真值"在诞生时就同时装着两份冲突文档。这是把冲突延后,不是消除。

**3. 语义错误修正——是否真修,还是只同步没改?**
只同步没改,且更严重。全量 `cp` 会把**仍引用已退役 Claude Code 的 unified 文档**原样提交进 git,commit message 却宣告"建立单一真值"。让"真值"在诞生时就包含已知虚假陈述(CC 未退役),是自相矛盾。CC 引用的修正必须**前置到同步 commit 之内或之前**,否则违反 §五.4(权威唯一,但权威是错的)。

**4. 时序版本机制——是否自动化校验,还是靠人工纪律?**
仍靠人工纪律。§5.3 的 `/truth/versions` 端点被定位为"后续基础设施",不在本方案执行范围;D3 的 pre-merge hook 只覆盖分支合并,不覆盖 local↔git 分叉这个**本次乱象的真正根因**。§5.1"今后直接在 git 做"是一句纪律承诺,没有任何强制物理约束。这与"零认知负担/自动运转"的北极星终局相悖。

**5. 不可委托敬畏——文档去留是否正确留给用户?**
这一维处理得最好。§4.1(先出清单不批量删)、§4.3(红线授权)、文档3节点3(用户逐份确认)都到位。唯一瑕疵:D1 预设"唯一权威规则**推测应该是** unified",这是对用户战略决策的锚定,应改为开放待裁,尤其 unified 恰恰是那份含语义错误的文档,不宜预设为权威。

---

## 二、架构级风险(5 个)

1. **真值诞生即污染(最高优先)**:同步早于清理,导致 git 在被宣告为"单一真值"的同一刻,内含 CC 语义错误 + unified/workspace 双份冲突。真值完整性在起点即被破坏。

2. **密钥同步存在实际命令级缺陷**:文档2 §2.3 声称 `archive/cc-retirement`"绝对不复制",但 Step 2 的循环 `for d in archive ...; cp -r ~/.agent-collaboration/$d/* $d/` **会把含明文 token 的 cc-retirement 目录物理拷进 git 工作区**,仅靠 Step 3 的 .gitignore 不跟踪来兜底。命令与红线声明直接矛盾;一旦 .gitignore 笔误或 `git add -f`,即泄露。爆炸半径高(且这些 token 无论如何都应轮换)。

3. **单一存储决策悬空**:X/Y/Z 未决,无 forcing function。Z 结构性违反 §三.3 却被并列。只有 X(软链,使分叉物理上不可能)或 Y 满足红线。

4. **真值仓库自身位于待治理区**:唯一真值落在 `~/Documents/trae_projects/agent-collaboration-standard`,而文档1把 `~/Documents/trae_projects/` 整片标为"散落项目目录待治理"。权威存储住在自己要清扫的房间里,位置未规范化。

5. **`cp` 覆盖非镜像**:Step 2 用 `cp -r .../standards/* governance/` 是**叠加式覆盖,不删除** local 已删文件,git 里会残留过时 governance 文档——又制造"多份权威",与 §五.4 冲突。真镜像需 `rsync --delete` + 人工确认删除项。

---

## 三、改进建议(3 条)

1. **让"单一真值"干净诞生——解耦"快照"与"权威声明"**:把本次同步降级为**归档快照 commit**(commit message 如实标注"含已知缺陷:CC 引用未改、unified/workspace 待合并"),把"单一真值已建立"的声明推迟到 D1 完成之后;或反过来,把 CC 引用修正 + unified/workspace 去留决策前置进同步 commit。二选一,但绝不能在带缺陷时对外宣告真值成立。

2. **现在就逼出单一存储决策,并推荐 X/Y、否决 Z**:从第一性原理,只有物理上消除第二个可写入口(软链 X 或消除 Y)才满足 §三.3;Z 是"治标"应剔除。同时规范化/迁移真值仓库出治理区,并把路径引用批量改到规范路径(选 Y 本就需要)。

3. **把自动化校验从"后续"提前为退出条件的一部分**:最小可行守护即可——(a)一个 grep 退役工具名(Claude Code/Codex/QoderWork)的 doc-linter,防语义错误回归;(b)若选 X 则分叉天然消失、无需校验,若暂未选 X 则加一个 local↔git 定时 diff 告警。让"自动运转"成为门槛而非 nice-to-have,否则根因未除。

---

## 四、评审结论:**有条件通过**

方案的风险控制与不可委托设计足够扎实,不构成"不通过";但"建立单一真值"的核心命题在当前形态下**逻辑上未成立**(同步传播已知缺陷 + 存储决策悬空 + Step 2 密钥拷贝缺陷),不能带着这三点进入执行。

**放行条件(三项须全部满足):**
- 修正或显式隔离"真值诞生污染"(CC 引用 + unified/workspace 冗余,在宣告真值前处理);
- 逼出单一存储决策并否决选项 Z;
- 修复 Step 2 对 cc-retirement 的实际拷贝缺陷(改为源头不 `cp`,而非仅靠 .gitignore),并至少承诺一个最小自动化守护。

满足后我方转为无条件通过。以上第 1、2 项为**硬门槛**,建议连同选项 X/Y/Z 一并列入用户裁决。
