## D2【识别逻辑漏洞】—— **FAIL**

**漏洞 1（必修）**：`truth_patterns` 只列 `reviewer-tiers.yaml / governance-review-process.md / .zcode/config.json`,但真值层实际至少还包括：
- `review-sessions-index.yaml`（review 调度真相）
- `pre-commit-review-gate-log.yaml`（gate 判定审计）
- `AGENTS.md`（准则本身）
- `.agents/rules/*.md`（子规则）

若 SO-11-v2-2 之后新增的真值文件未同步进 patterns，会出现"改真值不拦"的静默漏防。**建议改为白名单目录 + 显式扩展点**（例如从 `.agents/rules/truth-files.yaml` 读取清单，让真值层自描述）。

**漏洞 2（必修）**：正则 `>\s` 要求 `>` 后有空格，以下写法全漏：
```bash
echo x >reviewer-tiers.yaml            # 无空格
python -c "open('reviewer-tiers.yaml','w').write(...)"  # Python 写
: > reviewer-tiers.yaml                # 截断（有空格但语义特殊）
cp /tmp/x reviewer-tiers.yaml          # cp 覆盖
mv /tmp/x reviewer-tiers.yaml          # mv 覆盖
install -m 644 x reviewer-tiers.yaml
truncate -s 0 reviewer-tiers.yaml
```
修法：把重定向正则改成 `>+\s*` 且**并列检测 `cp/mv/install/truncate/python -c.*open.*w` 等写入动作**，或者反向——只要目标文件是真值层且命令非只读工具（cat/less/head/tail/grep/wc/stat/ls/git diff/git log），就拦。

**漏洞 3（建议）**：mira 评审识别复用 chain-gate 关键字。**耦合风险确实存在**——若 chain-gate 的 YAML 关键字表损坏，bootstrap-gate 的 mira 分支要么全放（漏拦评审）要么全拦（误伤日常 mira 调用）。建议 bootstrap-gate 自带一份最小关键字子集（`review|评审|审查|check|verdict`）作为 fallback，不完全依赖 chain-gate。

## D3【规则冲突】—— **FAIL（顺序错位）**

**核心问题**：bootstrap-gate 放在 PreToolUse 第 4 位是**错的**。

- Claude Code / zcode 的 hook 链一旦某个 hook 返回 deny/exit≠0，**后续 hook 不会执行**（这是链式短路语义）。
- 意味着：如果前 3 个 hook（chain-gate 等）因为它们自己的 YAML/state 损坏而 deny，bootstrap-gate 根本没机会跑，**但 chain-gate 的"损坏"本身可能就是 compact 续接遗漏 bootstrap 导致的**——鸡生蛋。
- 反之，如果前 3 个 hook 放行了一个动手命令但 bootstrap 未做，bootstrap-gate 才在最后兜底，**中间那 3 个 hook 的"放行"决策其实建立在无 bootstrap 前提上，本身不可信**。

**必修**：bootstrap-gate 必须放 **PreToolUse 第 1 位**。语义上它是所有下游 hook 的前置条件——"没 bootstrap 一切免谈"。前 3 个 hook 应当能假定 bootstrap 已完成才做判定。

顺带：若前置 hook 顺序调整困难，至少要求 bootstrap-gate 在自己的输出里显式声明"我先跑"，并在文档里锁定顺序契约。

---

## D4【数据一致性】—— **FAIL（路径歧义）**

**必修**：标记路径必须明确。当前描述里出现两个位置：
- 任务描述："`~/.zcode/hooks/.bootstrap-done.json`"（home 级）
- hook 实际位置："project 级 `.zcode/hooks/`"

两个语义完全不同：
| 位置 | 含义 | 风险 |
|---|---|---|
| home 级 | 跨 project 共享标记 | A 项目 bootstrap 完，B 项目也被认为 OK → **严重误放** |
| project 级 | 每个 project 独立 | 正确，但要注意 project 内多 session 覆盖 |

**建议**：标记路径应为 **project 级 + session_id 后缀**（例如 `.zcode/hooks/.bootstrap-done.<session_id>.json`），彻底消除跨 session 复用歧义；is_marker_valid 里的 `time_window` 兜底同时收紧到"仅当 session_id 文件不存在时才走时间窗"。

跨 session 复用的另一风险：compact 续接的新 session 若继承了旧 marker 且 session_id 不同，会掉进 time_window 分支——这**恰好是本次 SO-12 要防的场景**。当前 8h 窗口太宽，实际 compact 可能发生在 30min 内的密集会话中，建议窗口缩到 **1h** 或干脆**禁用 time_window 兜底**，让 session_id 不匹配就 deny，强制重跑 SessionStart。

## D5【配置健壮性】—— **CONDITIONAL**

- **fail-closed 方向对**：SessionStart 失败 → 无标记 → bootstrap-gate 拦，✅。
- **但 SessionStart 无单测**是硬伤（必修）：整个机制的"真值注入"环节零覆盖，等于把 gate 建在无验证的地基上。至少需要 3 个 case：三件套齐全、缺 1 个、全缺 → 分别验证注入内容 + 标记写入行为。
- **additionalContext 体积成本**：5-10KB 每 session 注入一次，token 成本可接受（相比 compact 事故的重跑成本），但**建议做 diff 注入**——只注入自上次标记以来变化的真值段落，减少稳定态开销；同时把三件套的 SHA 记进标记，SessionStart 时若 SHA 未变可跳过 additionalContext 只更新标记。

---

## D6【与现有 hook 共存】—— **CONDITIONAL**

- **hook 数量**：6 个（4 PreToolUse + 1 PostToolUse + 1 SessionStart），量级本身可接受，但**每次动手类 Bash 触发 4 个 PreToolUse 串行**，延迟叠加需实测。建议加一条性能预算：**PreToolUse 链总耗时 P95 < 200ms**，超过就拆并行或引入短路缓存。
- **IO 成本**：bootstrap-gate 每次读标记文件 → 一次 stat + 一次 read（<1KB），冷缓存 <5ms，热缓存 <1ms，**可接受**。但如果标记路径歧义（见 D4）需要多路径 fallback 查找，IO 会翻倍，修完 D4 就没问题。
- **建议**：给 bootstrap-gate 加一个进程内 in-memory 缓存（同一 session 首次读后缓存 60s），避免同一 session 内高频动手命令重复读文件。
