# 评审方 B — 节点 1 二轮重审结论

**结论：不通过。5 项阻断均未真正闭环。**

v3.0 的方向明显改善，但当前仍存在执行顺序错误、文档与脚本矛盾、验收不可复现等问题。其中 **B.1 的暂存区扫描顺序错误属于立即阻断**：按现有步骤执行时，secret 扫描基本不会扫描本次导入内容。

## 逐条复核

| # | 原阻断 | 结论 | 核心原因 |
|---|---|---|---|
| 1 | secret 扫描重写 | **未闭环** | 扫描发生在 `git add .` 之前，暂存区为空；文档仍内嵌敏感模式片段 |
| 2 | 策略语义明确 | **部分修复，未闭环** | 策略命名清楚了，但策略表、实际命令、验证方式仍不完全一致 |
| 3 | 词表与历史例外 | **未闭环** | 自动脚本无差别替换历史引用，与例外原则冲突；机器判定没有实现 |
| 4 | 两套回滚模型 | **部分修复，未闭环** | 概念拆开了，但普通回滚和泄密清洗仍缺少可安全执行的完整步骤 |
| 5 | 10 条量化门禁 | **未闭环** | 只有指标清单，没有生成证据和逐项判定的可执行机制 |

## B.1 secret 扫描：未闭环

### 阻断问题

执行顺序目前是：

1. Step 2 导入文件；
2. Step 4 执行 `git diff --cached --name-only`；
3. Step 5 才执行 `git add .`。

因此 Step 4 扫描时，本次变更尚未进入暂存区，`git diff --cached --name-only` 通常为空。即使工作树里已经导入敏感内容，检查也可能以零命中通过。

这是实质性漏检，不是文档表述问题。

### 其他未闭环点

1. 文档宣称“方案文档不含任何 token 片段”，但“patterns 文件”示例仍直接列出了敏感固定字符串或其片段，与修订目标自相矛盾。
2. `xargs grep` 未使用 NUL 分隔，不能可靠处理带空格、换行等特殊字符的文件名。
3. 暂存区中包含删除路径时，直接把文件名交给 `grep` 会出现文件不存在问题。
4. 未检查 patterns 文件是否：
   - 存在；
   - 可读；
   - 至少含一个有效模式；
   - 本身位于仓库外且未被软链接或复制进仓库。
5. 所谓“全文件类型”仍未完全成立：
   - 当前逻辑本质上按工作树文件路径执行 `grep`；
   - 不能精确扫描暂存区 blob；
   - 对二进制内容、删除文件及特殊路径不够可靠。
6. 修订对照中提到“高熵通用正则”，实际实现只有 `grep -F` 固定字符串，没有高熵或通用凭证检测。

### 必须修正

至少应调整为：

1. 导入完成；
2. `git add -A`；
3. 对暂存区实际内容执行扫描；
4. 扫描通过后才允许 commit。

建议直接扫描 staged patch 或 staged blob，而不是从 `--name-only` 回到工作树读取文件。固定敏感值扫描与通用凭证/高熵扫描应分成两层，并明确各自误报豁免机制。

## B.2 同步策略语义：部分修复，未闭环

### 已改善

- 已明确区分 `mirror`、`selective-mirror`、`add-only`、不导入和不动。
- mirror 类命令使用了 `--delete`。
- archive 排除项已显式列出。

### 尚未闭环

1. **策略表与执行命令不一致。**  
   `standards/ → governance/` 的策略表包含一个排除规则，但 Step 2 的通用 mirror 循环没有对应排除参数。

2. **add-only 的实际范围被缩窄。**  
   策略声明同步 `templates/` 和 `docs/`，命令却只处理顶层 `*.md`：
   - 不处理子目录；
   - 不处理非 Markdown 文件；
   - 空目录或没有匹配文件时，shell glob 行为可能产生错误输入。

3. **没有真正执行 dry-run。**  
   文档承诺“dry-run 输出新增/修改/删除/排除清单”，但 Step 4 只是运行：

   `git diff --cached --stat`

   这不是 `rsync --dry-run`，也不能证明实际同步与预期策略一致。

4. **selective-mirror 的排除语义缺少验证。**  
   应证明排除项既未复制，也未因 `--delete` 被误删，并将结果固化为证据。

### 必须修正

- 为每个映射生成独立、确定性的 dry-run manifest。
- manifest 至少区分新增、修改、删除、排除。
- add-only 应明确是“目录递归 add-only”还是“仅顶层 Markdown add-only”；策略表和脚本必须完全一致。
- 实际执行后再生成 staged manifest，与 dry-run manifest 做机器比较。

## B.3 词表与历史例外：未闭环

### 核心矛盾

处理原则规定：

- 角色引用替换；
- 历史叙述保留并进入例外清单。

但 A.2 脚本对四个词执行无差别全局替换，既不判断 `[ROLE]`，也不保留 `[HISTORY]`。这会直接改写历史叙述，与声明的历史例外机制冲突。

目前只有 “Trae IDE” 被要求逐条人工分类，其他退役词没有同等分类流程。

### 其他问题

1. `for f in $(find ...)` 不能安全处理带空格或换行的路径。
2. 对所有 `-type f` 执行 `sed -i`，可能修改二进制文件或非文本资产。
3. 退役占位符在不同章节中的写法不一致，无法稳定机器匹配。
4. “现行 0、历史 100%”只有目标，没有：
   - 现行与历史范围的机器定义；
   - 例外清单 schema；
   - 命中项与清单逐项匹配脚本；
   - 过期行号、文件移动后的稳定标识处理。
5. 例外清单又被 archive 同步显式排除，因此节点 2 若只审仓库 commit，无法验证“历史引用 100% 命中已批准清单”。

### 必须修正

- 所有退役词统一执行 `[ROLE]/[HISTORY]` 分类，不能只对一个词分类。
- 例外记录应使用稳定标识，例如文件路径、内容摘要或行内容 hash，而不能只依赖行号。
- 提供机器校验：
  - 未登记的退役词命中数为 0；
  - 每个保留命中都对应一条已批准例外；
  - 每条例外都能反向匹配一个实际命中；
  - 无失效、重复或悬空例外。
- 例外证据必须进入节点 2 可访问、可审计的证据包；不能一边排除入库，一边要求评审基于同一 commit 复核。

## B.4 两套回滚模型：部分修复，未闭环

### 已改善

泄密事件已经明确包含：

- 先撤销或轮换凭证；
- 调查传播范围；
- 清理 Git 历史；
- 禁止把 revert 当作泄密处置完成。

方向正确。

### 尚未闭环

#### 普通内容回滚

1. “`reset --hard` + 清理 untracked”中的清理命令和保护范围未定义。
2. 未明确清理 untracked 前必须预览，可能误删同步前已有的本地未跟踪文件。
3. push 后仅删除远程分支，不会恢复本地工作树和本地分支。
4. 已合并后的 `git revert <merge-commit>` 对 merge commit 通常需要明确主线参数，当前命令并不完整。
5. 文档宣称 Step 1 已加入 `reset --hard` 红线提示，但 Step 1 实际没有该提示。

#### 泄密事件回滚

1. `git filter-repo` / BFG 仅作为二选一名称出现，没有明确：
   - 清理哪些 refs；
   - tag、远程跟踪引用、备份引用如何处理；
   - reflog 和本地对象何时清理；
   - 多 clone 如何验证。
2. “全机扫描”没有定义扫描范围、工具、输出格式和通过标准。
3. 强制推送范围不明确，可能只更新当前分支而遗漏其他受污染分支或 tag。
4. secret 扫描命中可能是 push 前阻断或误报，不应一概直接升级为已经泄密并要求撤销凭证；应区分：
   - 本地预提交命中；
   - 已 commit 未 push；
   - 已 push/进入外部系统；
   - 已确认误报。

### 必须修正

为两套流程分别给出：

- 前置条件；
- 精确命令或操作清单；
- 数据保护措施；
- 完成定义；
- 可保存的验证证据。

泄密流程还需按传播阶段分级，不能只使用一条统一处置路径。

## B.5 十条量化门禁：未闭环

目前增加了十条指标，但没有形成可执行验收。尤其是：

1. 门禁 1 没有同时检查工作树、index、tracked refs 和历史对象。
2. 门禁 3、4 没有对应校验命令。
3. 门禁 5 没有生成映射级 manifest。
4. 门禁 6 没有 dry-run 基线，因而无法比较“差异为 0”。
5. 门禁 7 没有从策略清单反向检查所有源目录和目标路径。
6. 门禁 8、9 需要记录 commit SHA 和签署结果，但没有证据格式。
7. 门禁 10 只要求保存证据，却没有规定：
   - 保存路径；
   - 文件格式；
   - 生成命令；
   - 与 commit SHA 的绑定方式；
   - 如何避免证据文件本身泄密。
8. Step 4 的 `git status` 和 `git diff --stat` 仍然依赖人工观察，不能支撑“硬门禁”。

### 必须修正

节点 2 之前应提供一个可重复执行的验收入口，输出结构化结果，例如：

- commit SHA；
- 每条门禁的 PASS/FAIL；
- 实测值；
- 证据文件路径及摘要；
- dry-run/actual manifest；
- 三方评审与用户批准所绑定的 SHA。

脚本必须非零退出阻断任何失败项，而不能只打印统计供人工判断。

---

# 最终裁定

**B：不通过，5 个阻断继续保留。**

本轮不是“完全没有修复”：策略分类、泄密处置理念和门禁目录均已有明显进展；但按照“是否真正闭环，而不是部分响应”的评审口径，当前仍不能进入节点 2。
