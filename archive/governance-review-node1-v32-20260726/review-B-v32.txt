## 仍然阻断的具体问题

### 1. B.1：`git grep --cached` 仍然是 fail-open

这段代码会吞掉 `git grep` 的执行错误：

```bash
hits=$(git grep --cached -l -F "$pattern" 2>/dev/null | head -1)
```

因为管道最终状态通常取 `head` 的退出码，以下情况都可能被当成“零命中”：

- `git grep` 执行失败；
- Git/index 状态异常；
- pattern 被错误解析为选项；
- 其他扫描错误。

必须区分：

- 返回码 `0`：有命中；
- 返回码 `1`：正常、无命中；
- 返回码 `>1`：扫描失败，必须立即阻断。

同时建议使用 `-e "$pattern"`，避免以 `-` 开头的 pattern 被解释为参数。

另外，示例 patterns 文件带有行尾注释。若填写真实前缀时保留注释，实际扫描内容会变成“前缀 + 注释”，导致永远匹配不到。必须明确：

- 每个有效 pattern 行只能包含固定字符串；或
- 解析时可靠移除行尾注释。

因此 **“改成 git grep --cached”只完成了扫描对象修复，尚未完成扫描失败阻断**。

### 2. B.3：ROLE 替换脚本实际执行失败

这里删除了工具名中的所有空格：

```bash
tool=$(echo "$tool" | tr -d ' ')
```

会产生：

- `Claude Code` → `ClaudeCode`
- `Trae IDE` → `TraeIDE`

但后续 `case` 仍匹配带空格的名称：

```bash
"Claude Code")
"Trae IDE")
```

因此这两个分支永远不会命中，`placeholder` 可能为空，替换不能按设计完成。

此外还有两个硬问题：

1. A.5 的机器验证遗漏了 `claude-zhipu`。
2. “历史引用 100% 命中例外清单”只打印数量，没有在不一致时 `exit 1`，并且文档明确写了“需人工核对覆盖率”，所以门禁 4 仍不是硬门禁。

单纯比较数量也不足以证明 100% 覆盖。必须按至少以下键做集合比对：

```text
文件 + 行号 + 工具名 + HISTORY 标注
```

任何实际历史命中未出现在批准清单中，都必须失败。

因此 **“生成清单 → 人工标注 → 只替换 ROLE”的方案方向正确，但执行实现尚未闭环**。

### 3. B.5：10 条门禁尚未真正落地

当前 Step 4 实际保存的主要是：

- cc-retirement 工作树检查；
- pattern 数；
- 暂存文件数；
- secret 命中数；
- diff stat。

但以下门禁没有对应的机器执行、失败条件及证据：

- 门禁 4：历史引用例外覆盖率 100%；
- 门禁 5：各映射新增/修改/删除/排除数量；
- 门禁 6：dry-run 与实际暂存区差异为 0；
- 门禁 7：未声明策略或目标路径为 0；
- 门禁 8：三位评审对应同一 commit SHA；
- 门禁 9：用户批准同一 commit SHA。

另外，`.review-evidence/` 的 `.gitignore` 规则是在 `git add .` **之后**追加的：

```bash
git add .
...
echo '.review-evidence/' >> .gitignore
```

这会导致 `.gitignore` 修改未进入暂存区，后续 commit 后工作树仍然脏；仓库提交中也没有该忽略规则。应在第一次 `git add .` 前完成 `.gitignore` 修改，或者追加后重新：

```bash
git add .gitignore
```

并重新执行暂存区扫描、计数、状态检查和证据生成。
