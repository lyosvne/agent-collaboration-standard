# 评审方 B｜节点 1 重审结论

## 结论：**不通过**

v2.0 对 5 个阻断点均作出了响应，但仍然是**部分修复，没有任何一项达到完整闭环**。其中第 2、4、5 项仍属明确硬阻断；第 1、3 项存在会导致方案失效的实现缺陷。

| 原阻断点 | 复核状态 | 结论 |
|---|---|---|
| 1. 敏感文件误纳管 | 部分解决 | 仍阻断 |
| 2. 精确同步与命令不一致 | 未解决 | 仍阻断 |
| 3. 错误内容被提升为权威真值 | 部分解决 | 仍阻断 |
| 4. 回滚与泄密处置模型不完整 | 未解决 | 仍阻断 |
| 5. 评审机制缺可量化门禁 | 未解决 | 仍阻断 |

## 1. 敏感文件误纳管：方向正确，但实现仍不可执行

白名单导入和 `rsync --exclude` 已解决 v1.0 中 `cp -r archive/*` 的直接矛盾，但还有三个问题：

1. `SECRET_HITS` 的首个 `grep -E` 模式使用方括号，正则会将其解释为**字符类**，而不是完整敏感串。它会匹配大量普通文本，导致检查几乎必然误报并停止提交。
2. 扫描仅覆盖 `md/json/jsonl`，不能发现 YAML、Shell、Python、环境文件、无扩展名文件以及二进制文件中的敏感内容。
3. `.gitignore` 不是有效的第三层安全防御：它不能阻止已经被跟踪的文件，也不能证明敏感内容没有进入 Git 对象库。

此外，Step 3 使用 `cat > .gitignore` 会**覆盖仓库原有忽略规则**，引入新的误纳管风险。

**必须修订：**

- 敏感串使用固定字符串扫描，或对正则元字符进行严格转义。
- 扫描 `git diff --cached --binary`、新增文件清单和待提交对象，而不是仅按三个扩展名递归扫描工作区。
- 将 `.gitignore` 改为保留原内容的幂等追加，并检查规则是否已经存在。
- 增加 `git check-ignore`、`git ls-files` 和暂存区禁止路径检查，结果必须为零。

## 2. 精确同步与实际命令不一致：仍未解决

v2.0 继续同时声明“最新内容同步”和“不覆盖模式”，但实际行为有三种不同语义：

- `rsync -a` 会覆盖 `governance/`、`archive/`、`audits/` 等目标目录中的同名文件；
- `templates/`、`docs/`、`LOCAL-USAGE.md` 只新增、不更新，已有文件即使落后也不会同步；
- 未使用 `--delete`，源端已删除的文件会继续残留在目标端。

因此该方案既不是精确镜像，也不是统一的不覆盖式导入，而是**按目录采用不同且未正式定义的合并策略**。

**必须修订：**

1. 为每个映射明确声明策略：`mirror`、`overwrite`、`add-only` 或 `manual-merge`。
2. 为每种策略提供相符的命令。
3. 执行前输出 dry-run 清单，至少区分新增、修改、删除、冲突和排除文件。
4. 若目标确实是“精确同步”，必须给出文件清单或哈希比对及删除语义；否则应将全文改称“选择性抢救导入”，不得继续使用精确同步表述。

## 3. 错误内容被提升为权威真值：降级声明不足以消除风险

Phase A 和 commit 降级声明降低了风险，但没有形成有效门禁：

1. A.1 词表没有 `Trae IDE`，但 1.1、A.3 又声明需要扫描或标记它，规范内部仍然矛盾。
2. Phase A 只扫描 `standards/templates/configs`，但本次还会导入 `docs/registry/project-starter/audits/archive`；这些目录里的现行指令可能未经处理进入仓库。
3. “编队角色”与“历史叙述”的分类没有机器可判定规则、人工审查清单或例外登记。
4. 已知存在冲突的文档仍会被合并进主仓库。commit 声明“不构成真值建立”不能改变其进入 `master` 后被其他工具读取和引用的事实。
5. Phase C 只有“三方一致”，没有规定如何证明活动性错误引用已经归零。

**必须修订：**

- 统一退役词表，并解决 `Trae IDE` 是否退役的内部矛盾。
- 扩大扫描范围至所有拟进入暂存区的文本内容。
- 对允许保留的历史引用建立逐项例外清单，包含文件、行号、理由和审核人。
- 对未裁决的冲突文档增加显式隔离或非规范性标识，避免被默认解析为现行规范。
- 门禁应为：现行指令中的退役角色引用 **0 个**；历史引用必须全部命中已批准例外清单。

## 4. 回滚与泄密处置：仍明显不完整

现有命令只能回退工作树或分支，不能处理已经传播的敏感信息：

- `git reset --hard` 不删除新增的未跟踪文件；
- 删除远端 sync 分支不保证相关 Git 对象、PR 引用、CI 产物、缓存或本地克隆消失；
- `git revert` 只产生反向提交，泄密内容仍保留在历史中；
- 没有密钥撤销、轮换、影响范围调查、历史清洗、强制更新审批、通知与复核流程；
- 没有区分“普通内容错误回滚”和“敏感信息泄露事件处置”。

**必须拆成两套模型：**

1. **普通内容回滚**：恢复 tracked 文件、处理 untracked 文件、验证工作区和远端分支状态。
2. **泄密事件处置**：立即停止 push/merge、撤销并轮换凭证、调查传播范围、清理 Git 历史及相关引用、处理 CI/制品/缓存、通知相关人员，并在重新开放前再次执行零残留验证。

在泄密场景中，`revert` 和删除分支不得被描述为完成处置。

## 5. 可量化评审门禁：仍未建立

“三方一致通过”属于审批规则，不是验收标准。当前只有若干命令，没有明确的预期值、失败条件和证据产物。

节点 2 至少需要以下硬门禁：

1. 禁止目录进入工作树、暂存区及 tracked 清单：**0 个**。
2. 敏感信息扫描命中：**0 个未豁免命中**。
3. 现行规范中的退役角色引用：**0 个**。
4. 历史引用：**100% 命中已批准例外清单**。
5. 每个源—目标映射的新增、修改、删除、排除数量均有清单并经审核。
6. dry-run 与实际暂存区文件集合差异：**0 个**。
7. 未声明覆盖、未声明删除和未声明目标路径：**0 个**。
8. 三位评审者必须针对同一 commit SHA 评审，批准数为 **3/3**。
9. 用户批准的也必须是同一 commit SHA；批准后若 commit 改变，评审自动失效。
10. 所有门禁输出应保存为可复核证据，而不是只在终端人工观察。

## 最终裁定

v2.0 **不能进入 Phase A/B 执行授权**。下一版无需重审全文，但必须提交针对以上问题的修订 diff，重点包括：

- 修复 secret 扫描正则和扫描范围；
- 明确定义逐目录同步语义；
- 建立退役引用例外清单和零活动引用门禁；
- 补齐泄密事件处置流程；
- 将节点 2 改造成基于同一 commit SHA 的可量化验收。

**评审方 B 状态：不通过，5 个原阻断点继续保留。**
