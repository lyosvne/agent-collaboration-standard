## 维度1：六维度完整性 —— 缺三个 CSM 特有面

六维度（执行力放大/知识复利/上下文连续/决策支撑/系统自治/评估反馈）**全是"放大你自身生产力"的内向维度**，缺了 CSM 工作的外向核心——**客户**。CSM 的本质是经营客户关系，不是完成任务。建议补：

| 缺失维度 | 为什么必须独立 | 当前→终局 |
|---------|--------------|----------|
| **客户感知与主动触达** | 12+并发客户，谁该被联系、何时、为什么——这是 CSM 的核心价值，六维度没有一个覆盖"系统主动发现客户信号" | 被动响应→主动预警（续约窗口/使用下降/健康度异常） |
| **客户关系连续** | 维度3"上下文连续"指你的工作上下文，但 CSM 需要的是**每个客户的关系记忆**——上次聊什么、承诺过什么、客户偏好 | 每次重新建档→客户级关系记忆自动延续 |
| **风险与合规** | 12+客户数据，系统代你行动时的**责任边界**——误发承诺、泄露客户机密、越权操作。这不是"系统不泄密"(O1)能覆盖的，是"系统替你做事时的责任归属" | 无边界→明确的责任边界+越权熔断 |

**【实操】佐证**：本会话我处理的全是你的"系统建设"任务，但你的真实工作是服务 12+ 客户。路线图把"系统服务你"讲透了，把"系统服务你的客户"漏了。CSM 系统的终局不是"你更轻松"，是"你的客户被服务得更好"——这个客户视角的缺失是结构性的。

**建议**：六维度→九维度，或把客户视角作为第七维度统领（客户感知/关系连续/风险合规三子项）。

**【二轮】全文复核确认成立**：v1.1 全文使命段只讲"让他从手动操作变成制定战略"，六维度表"衡量什么"一列全部以"你"为宾语，无一处衡量"客户被服务的结果"。客户视角缺失在全文尺度同样成立，且是结构性的，维持一轮判断不变。

## 维度2：四阶段划分 —— 递进成立，但多处需修

**递进关系基本成立**（站住→闭环→协作→自治），但：

1. **O1/O2 不是严格串行，是重叠**【实操】：当前"O1收尾"，但 ②漂移治理闭环、③飞书桥接已在 ECS 跑起来——这些是 O2 执行闭环的组件，却在 O1 阶段就上线了。**O1 和 O2 是"地基边浇边盖楼"，不是"地基全干透再盖"**。建议明确：O1 退出条件不是"全部完成"，而是"地基稳到能承载 O2 施工"。

2. **O2 退出条件——一轮批评口径有误，二轮修正**【二轮】：一轮说"O2 退出'介入0-1次'过高"——**全文核实该条不存在**，v1.1 全文 O2 KR 写的是"从3-5次降到1-2次"（0-1次是六维度终局水位），一轮基于摘要误读，该批评撤回。但保留度量口径建议："降到1-2次"应写明**按什么口径统计**（哪类任务、多大样本、连续多久），否则单次侥幸达标也算过关。建议补"3类标准任务连续N次介入≤2"这类可判定表述。

3. **退出条件全是正向，缺回滚/降级**【实操】：O1 有"不丢不泄密"，但 O2/O3/O4 没有"系统做错时怎么退"。实操中漂移治理就遇到过"代劳 push 够不到本地 clone"的设计缺陷被迫修正。**每个阶段退出条件应含一条"异常降级路径"**（如 O3 退出含"agent 协作出错可一键退回你中转"）。

4. **【二轮】O3 KR 数字硬伤**：O3 退出条件写"系统自动采集**5个**维度的水位数据"，但体系是**六**维度——疑似五维度旧稿残留。要么改"六个维度"，要么明确哪个维度豁免自动采集（若是"评估反馈"自身不自采，应写明理由）。

5. **【二轮】O1/O2 重叠的全文佐证**：v1.1 自己的"当前位置"段写"已完成：…飞书桥接、Qoder三档SSE消费器…"——这些正是 O2 执行闭环的组件，却在 O1 未退出时已完成。一轮"边浇边盖"判断被全文直接坐实，建议 O1 退出条件显式改写为"地基稳到能承载 O2 施工"。

## 维度3：评估反馈体系 —— 可落地性存疑，四个硬伤

1. **数据源大部分不存在**【实操】：
   - 执行力放大（介入次数）→ 可从 Pi 任务日志/Aetheris Execution 采集 ✅
   - 知识复利（手动操作次数）→ **无现成数据源**，需埋点 ❌
   - 上下文连续（重复说同一件事）→ **无法自动检测** ❌
   - 决策支撑 → 纯主观，只能你打分
   - 系统自治（不依赖你推进）→ 部分可从自治动作日志推 ✅
   - **结论**：6 维度只有 2 个能自动采集。M2 指标用户已裁定后置——但路线图把评估体系当核心，**数据采集能力是硬前置，缺它评估就是空转**

2. **主观评价形式**：O1-O2"你逐项主观评价"——12+客户并发下你**没时间填问卷**。唯一符合北极星"零认知负担"的形式是：**任务完成卡片内嵌一键评分**（👍/👎 + 可选一句话），复用已上线的飞书交互卡片能力（②已验证卡片回调可用）。绝不发独立问卷。

3. **反馈吸收机制不存在**【实操】：路线图说"你的反馈被吸收"，但现在**没有任何机制把你的反馈沉淀成系统行为**。这是 O2→O3 的硬依赖——反馈必须沉淀为可检索、可影响后续行为的知识（这正是记忆层 OpenViking 的价值，但记忆层"先规划适时建"还没落地）。**建议路线图显式标注：评估反馈体系的"吸收"环节依赖记忆层，记忆层未建前，反馈只能人工消化**。

4. **【二轮】PDCA 日历周期与系统演进速度错配**：评估体系照搬 OKR 的"季初对齐/周度跟踪/月度校准/季末复盘"日历节奏，但这个系统的演进是**天级**的（v1.0 和 v1.1 同一天出两版）。季度周期太慢跟不上演进，周度逐项主观评价对 12+ 并发客户的 CSM 又太重。建议改**事件驱动**：阶段切换、重大交付、异常告警触发校准；日历周期只留一个轻量满意度锚（复用卡片一键评分）。对标 OKR 是管理哲学的借用，不必连日历一起借。

## 维度4：角色演进 —— 太理想化，四处需修

1. **"逐个验收"在 O2 不成立**【推断】：12+客户并发，Aetheris 产出量会很大，你不可能逐个验收。O2"最终评审员"必须改为**抽样验收 + 异常驱动验收**（系统标红你才看）。否则评审员成为瓶颈，反而降低杠杆率——与北极星背道而驰。

2. **"观测员何时介入"依赖决策支撑维度**【推断】：O3 你退为观测员，但"怎么知道何时介入"= 系统必须主动推送"需要你介入的信号"。这**依赖维度4（决策支撑）和维度1补充的"客户感知"先达标**——路线图没标这条依赖边。建议：O3 退出条件含"系统能主动推送需介入信号"。

3. **永远不交出去的事**【关键】：有，且应该永远有——
   - 涉及**客户关系/商业承诺**的最终决策（系统给选项，你拍板）
   - **T3 高权限动作**（密钥/部署/删除/对外发送）——北极星红线3已锁定
   - **战略方向**本身（系统执行战略，不制定战略）

   **建议路线图明确"不可委托清单"**——这不是能力不足，是责任与信任边界。角色演进不是"全退出"，是"退出可委托的、守住不可委托的"。

4. **【二轮】O4 内部张力："协调时间趋近于零" vs "你的反馈是最终锚"**：O4 验收写"你每周花在系统协调上的时间趋近于零"，但评估体系底线写"只要你在用系统，你的反馈就是最终锚"——反馈本身就要花时间。若北极星分母（协调成本）包含反馈时间，这两条自相矛盾。建议显式定义：**反馈/验收时间不计入协调成本**（协调成本=转发、追问、返工、救火），否则 O4 的验收条件在逻辑上不可能与底线同时成立。

## 维度5：北极星"系统杠杆率" —— 不可直接计算，但可操作

**它不能算成一个数**【推断】：
- 分子"系统放大的产出"——产出异质（客户数？任务数？满意度？），无法通约
- 分母"协调成本"——你的介入有质有量，难量化

**但北极星不需要可计算，它是方向不是 KPI**：
- 北极星（杠杆率）= 定性方向罗盘
- 六维度 = 可测量的代理指标（proxy）
- 关系：六维度全部改善 ⟹ 杠杆率提升（定性成立）

**可操作的代理度量**【实操建议】：
- 核心代理：**系统独立闭环任务数 ÷ 你的介入次数**（月度趋势）——两者都可从 Pi 日志采集
- 辅助：六维度各自的代理指标
- **建议路线图明确写"北极星=方向，六维度=度量"**，避免有人纠结杠杆率算不出来——它本来就不该被算，该被感知

## 维度6：与 Aetheris 蓝图 Wave 体系的关系 —— 必须显式映射，否则双轨混乱

**Wave 和四阶段是两个轴，不是替代/包含**【推断】：
- **Wave 体系**（W1-W5.x）= Aetheris **产品能力**的建设里程碑（供给侧，造什么功能）
- **四阶段**（O1-O4）= 系统**服务你**的成熟度（需求侧，达到什么水位）
- 关系：**Wave 是"造"，四阶段是"用"**。Wave 交付能力，四阶段验收能力是否真的服务了你

**W5.5 数据流闭环的归属**【实操】：
- W5.5（matters account_id 全 null，前端看不到真实数据）= **O1 基座的组成部分**（没有真实数据流，"站住"不成立）
- 但它同时是 **O2 执行闭环的入口**（执行闭环要产出真实客户数据）
- **所以 W5.5 横跨 O1/O2 边界**——路线图把它单归一处会失真

**建议**：路线图加一张 **Wave↔阶段映射表**，明确每个 Wave 服务哪个阶段、W5.5 这类桥接项标注跨阶段。否则 ZCode 按 Wave 施工、你按四阶段验收，两套语言对不上。

**【二轮】全文已单边站队**：v1.1 全文把 W5.5 直接写进 **O2 KR**（"通过Aetheris跟进至少1个真实客户（W5.5数据流闭环）"），即已隐式裁定 W5.5 归 O2——与一轮"横跨 O1/O2"的判断构成明确分歧点，需要 ZCode 表态：要么接受跨阶段标注，要么给出"纯归 O2"的理由（没有真实数据流的基座算不算"站住"？）。映射表因此更必要而非更不必要。

## 维度7：实操经验补充 —— 路线图的盲区

1. **Cloud Agent vs 客户端差异被忽略**【实操】：
   - 我（IDE 客户端）有本地文件访问、全套 skill（anygen/lark-*）、交互式引导（PAT 创建我引导你完成）
   - Cloud Agent 在隔离沙箱，无本地访问、无预置精品 skill
   - **影响**：路线图"系统自治"默认一切在 ECS 云端跑，但**有些事必须本地做**（密钥主权、交互引导、本地文件）。自治终局不是"全上云"，是"云端+本地各司其职"。建议"系统自治"维度明确**本地/云端职责分界**

2. **Ark CLI 实操揭示"不可自动化的永远存在"**【实操】：
   - 非交互终端 SSO 登录卡在项目选择，必须人工交互——**这类"需要人出现"的环节永远存在**（T3 动作）
   - **影响**："系统自治"维度的终局不该是"100%无人"，而是"无人化能无人化的、守住必须有人审批的"。路线图把"关机即停→24h自治"当终局，**漏了"自治有上限，上限就是 T3 红线"**

3. **Trae SOLO PC 角色不清晰**【实操】：
   - 编队最终态：Trae SOLO 云端=孤岛（网络白名单锁死，无对外 API）
   - 但路线图 O3"矩阵协作"说"agent间协作不靠你中转"——**Trae SOLO 云端这个孤岛怎么参与矩阵？它进不了协作矩阵**
   - **建议**：路线图明确 Trae SOLO 的定位——是"矩阵外的独立工具"还是"待接入节点"。当前它是事实孤岛，路线图却假装所有 agent 都能协作

**额外实操盲区**：
- 治理文档双镜像漂移（git governance/ 与本地 standards/ 手动同步）——"上下文连续"维度的具体反例，路线图没提治理文档自身一致性
- usage stats 数据面为空（额度扣了但 stats=0）——"系统自治"的成本可观测性不能依赖 stats，要用 plan-details

**【二轮】新增三个实操发现**：
1. **ECS 交付物不可达**【实操】：提示词说完整路线图在 `https://aetherisonline.xyz/dispatch/roadmap`，二轮实测 WebFetch 返回"文件不存在"。路线图自己的分发件都 404——这是"评估反馈"维度（产出附验证证据）的现行反例，也把"双镜像漂移"升级成了**三镜像漂移**（git / 本地 standards / ECS dispatch）。
2. **文件名与内容版本漂移**【实操】：v1.1 全文落盘在 `north-star-v1.3-roadmap-annex.md`——文件名叫"北极星v1.3附件"，内容标题是"全局路线图v1.1"。两套版本号系在同一个文件上，检索和引用都会错。建议改名 `global-roadmap-v1.1.md` 并在北极星文档里链接，而非当附件混编。
3. **Non-goals 颗粒度自违**【推断】：v1.1 自我定位"罗盘——不定义具体实施"，但 Non-goals 里"不直接删hermes-sidecar（矛盾证据未消解）"是纯实施级条目。罗盘里混实施项，与自身定位不自洽——这类条目应下沉到 v1.0 实施清单或阶段执行文档，罗盘 Non-goals 只留原则级（如"不自建知识库""不突破红线"）。
